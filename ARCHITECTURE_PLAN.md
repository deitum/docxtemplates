# План улучшения архитектуры

Разбор архитектуры [docxtemplater](https://github.com/open-xml-templating/docxtemplater)
(v3.69.3) и перенос применимых практик в `@deitum/docxtemplates`.

**Ограничение.** Контракт — поведенческий, не типовой: `createReport` и `listCommands`
принимают то же, что сейчас, и возвращают тот же результат — байт в байт тот же docx,
тот же массив команд, те же ошибки в тех же ситуациях. Имена экспортов, формы типов,
внутренняя структура — свободны. Всё, что видит пользователь, фиксировано; всё, что
за этим, — предмет плана.

Отправная точка (замерено на текущем `master`): 16 тестовых файлов, 392 теста,
покрытие 98.27% операторов / 94.89% ветвей, `src/` ≈ 3.5 тыс. строк без тестов.
Кодовая база в хорошем состоянии — план не про «навести порядок», а про конкретные
архитектурные решения, которые у docxtemplater сделаны лучше.

---

## 1. Чем архитектуры отличаются принципиально

|                         | docxtemplater                                                                                                    | текущий проект                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Представление шаблона   | плоский массив токенов (`lexed` → `parsed` → `postparsed`), работа со строками XML                               | полное DOM-дерево `Node`, построенное `sax`                              |
| Модель выполнения       | **компиляция один раз** → `render(data)` по скомпилированному AST                                                | один проход курсором по дереву с прыжками назад на каждой итерации `FOR` |
| Расширяемость           | всё — модули с хуками (`parse`, `postparse`, `resolve`, `render`, `postrender`, …); ядро не знает про циклы      | `switch` по `Command` в `commands/execute.ts` + поля фич в `Context`     |
| Async                   | отдельная фаза `resolve` (все промисы параллельно), затем синхронный `render`                                    | каждая команда `await`-ится последовательно внутри обхода                |
| Ошибки                  | `properties: { id, explanation, offset, xtag, file }`, агрегация в `properties.errors`                           | классы ошибок без позиции и без имени части документа                    |
| Правила структуры OOXML | декларативные таблицы в `file-type-config.js` (`tagShouldContain`, `expandTags`) + починка в `join-uncorrupt.js` | правила зашиты в `if`-цепочки внутри `walk.ts`                           |
| Состояние рендера       | `ScopeManager` — стек скоупов, состояние модулей живёт в модулях                                                 | один `Context` на 27 полей, из них 10 принадлежат IMAGE/LINK/HTML        |
| Валидация опций         | схема (`minizod`), `.strict()` — опечатка в опции падает                                                         | молчаливая коррекция (`errorHandler` не-функция просто игнорируется)     |
| Сериализация            | массив строк + один `join`, чанки по 64 КБ                                                                       | рекурсивный `Buffer.concat` на каждый узел                               |

### Что осознанно **не** копируем

**Строковый лексер вместо DOM.** docxtemplater не строит дерево — он режет сырой XML
на токены и склеивает строки обратно. Это быстрее и экономнее по памяти, но на дереве
держатся `IMAGE`/`LINK`/`HTML` (подстановка готового узла вместо `w:t`/`w:r`/`w:p` в
`walk.ts:moveOutputUp`), перенумерация `wp:docPr`/`v:shape` и склейка разорванных
Word-ом команд в `preprocessTemplate.ts`. Переход на строковый конвейер — переписывание
движка целиком ради выигрыша, который на порядок меньше, чем этап 1 этого плана. Отклонено.

**Публичный модульный API (`attachModule`).** Это новая публичная поверхность и новые
обязательства по совместимости. Внутренний реестр команд (§5) даёт ту же развязку
без публичного API.

## 2. Что теперь фиксировано, а что нет

Свобода в именах смещает границу: **контракт — это наблюдаемое поведение**, а не типы.

**Фиксировано (менять нельзя):**

- `createReport(options)` → тот же docx для тех же входов. Проверяется побайтово.
- `createReport(options, 'JS' | 'XML')` — отладочные перегрузки. На них построена
  бо́льшая часть тестов и снапшотов; остаются как есть.
- `listCommands(template, delimiter?, aliasOptions?)` → тот же массив `{ raw, type, code }`
  в том же порядке.
- `getMetadata(template)` → тот же объект.
- Семантика **каждой** опции `UserOptions`, включая значения по умолчанию.
- Поведение при ошибках: какие классы, в каких ситуациях, с какими сообщениями;
  бросок массива при `failFast: false`.
- Колбэки-опции как контракт вызова: `data` (`QueryResolver`), `errorHandler`,
  `runJs` — вызываются с тем же и в том же порядке.

**Свободно:**

- Имена и состав экспортов, разбиение `types.ts`, формы внутренних типов.
- Форма `Context` и `Node` — они протекали в `.d.ts`, но теперь это не сдерживает.
- Внутренняя модель выполнения целиком.

**Одна оговорка про `runJs`.** Он получает `{ sandbox, ctx }`. Документированный
пример (`examples/example-vm2/index.js`) использует только `sandbox`; из тестов
`ctx` трогает один — читает `ctx.options`. То есть сузить `ctx` до реально нужного
подмножества (`options`, `vars`, `loops`, `jsSandbox`) безопасно, но это решение
надо принять явно и упомянуть в changeset: у стороннего кода, который лезет в `ctx`
глубже, сломается типизация (поведение — нет, если поля сохранить).

## 3. Этап 0 — страховка (делать первым, без исключений)

План теперь допускает переписывание внутренностей движка. Единственное, что удерживает
результат на месте, — тесты. Значит первым делом надо превратить «тот же результат»
из обещания в проверку.

**Что сделать:**

1. **Золотой корпус.** Прогнать все фикстуры из `src/__tests__/fixtures/` (плюс
   `examples/example-node/*.docx`) через `createReport` с зафиксированными данными и
   сохранить **байты результата**. Тест сравнивает байты. Сегодня снапшоты снимаются
   с `_probe: 'XML'` — то есть только с `document.xml`; заголовки, колонтитулы,
   `.rels`, `[Content_Types].xml`, картинки в `word/media/` и порядок файлов в zip
   не проверяются ничем. Именно там живут регрессии этапов 3 и 6.
   Формат: распаковать zip, снять снапшот с отсортированного списка `путь → sha256`
   плюс полный текст XML-частей. Диффы должны читаться.
2. **Золотой `listCommands`** — снапшот для каждой фикстуры, включая шаблоны с алиасами
   и нестандартными разделителями.
3. **Снапшот публичной поверхности** — список экспортов и их `typeof`. Теперь это не
   запрет, а журнал: переименование должно быть видно в диффе и осознанно принято.
4. **`npm run bench`** — воспроизводимый бенчмарк (аналог `profile.bash` у docxtemplater):
   цикл `FOR` на N итераций, крупный статический документ, документ с изображениями;
   печатает мс по фазам (parse / preprocess / walk / build / zip). Без него утверждения
   этапа 1 нечем подтвердить, а этап 6 нечем оправдать.
5. Опционально: страж размера бандла (`verifypublishsize.bash` у docxtemplater).

**Критерий готовности этапа:** намеренно внесённая правка в `walk.ts` (например,
не удалять пустой абзац) должна ронять корпус, а не проходить незаметно.

**Риск:** нет. **Оценка:** ~1 день.

## 4. Этап 1 — производительность (изолированно, с замерами)

Два места, где текущая реализация проигрывает на порядок. Оба правятся локально,
не затрагивая модель выполнения, поэтому идут до всякой перестройки.

### 4.1. Sandbox: `vm.createContext` на каждое вычисление — главная потеря

`jsSandbox.ts:runUserJsAndGetRaw` на **каждый** вызов команды делает
`new vm.Script(code)` и `vm.createContext(sandbox)`. В цикле `FOR` — на каждой
итерации для каждой команды.

Замеры (6000 вычислений, Node 22):

| стратегия                                                          | время      |
| ------------------------------------------------------------------ | ---------- |
| `new vm.Script` + `vm.createContext` на вызов (**текущая**)        | **714 мс** |
| кэш `vm.Script`, `createContext` на вызов                          | 687 мс     |
| кэш `vm.Script` + переиспользование контекстифицированного объекта | **2.6 мс** |
| `new Function` (путь `noSandbox: true`)                            | 4.2 мс     |

Сквозной замер, отчёт с `FOR` × 2000 и тремя `INS` внутри (6000 вычислений):
**813 мс** против **50 мс** с `noSandbox: true`. То есть в шаблоне с циклами до 95%
времени генерации уходит на `vm.createContext`, а не на разбор, обход или zip.
Кэш скриптов сам по себе почти ничего не даёт (714 → 687) — платит именно
контекстификация объекта.

**Что взять у docxtemplater:** `cachedParsers[part.lIndex]` — скомпилированное
выражение живёт столько же, сколько скомпилированный шаблон, а не одно вычисление.

**Что сделать:**

- один контекстифицированный объект на часть документа (изоляция между `document.xml`
  и `header1.xml` сохраняется как сейчас);
- перед вызовом присваивать в него `data`, `additionalJsContext`, `$vars`, `$idx`,
  `__code__` вместо создания нового объекта;
- `Map<string, vm.Script>` для скомпилированного кода;
- снимок в `ctx.jsSandbox` после вызова оставить — именно он реализует документированное
  «состояние переносится между сниппетами».

**Осторожно:** состояние и так переносится (`ctx.jsSandbox` копируется целиком), поэтому
семантика не меняется — но это надо закрепить тестами **до** правки: `EXEC` объявляет
переменную, `INS` читает её позже; переменная из `document.xml` не видна в `header1.xml`;
`additionalJsContext` перекрывает значение, оставшееся от предыдущего сниппета;
`delete` переменной в сниппете.

**Риск:** средний (семантика песочницы). **Выигрыш:** ~×8 на шаблонах с циклами.
**Оценка:** ~0.5 дня.

### 4.2. `buildXml`: массив строк вместо рекурсивного `Buffer.concat`

`xml.ts:buildXml` на каждый узел собирает массив `Buffer` и делает `Buffer.concat`
рекурсивно — каждый байт копируется столько раз, какова его глубина в дереве.
docxtemplater в `postrender.js` накапливает строки и кодирует один раз чанками по 64 КБ.

Замер (20 000 абзацев, 1.65 МБ на выходе, вывод **побайтово идентичен**):

| реализация                 | время                 |
| -------------------------- | --------------------- |
| текущая                    | 23.8 / 25.4 / 31.3 мс |
| массив строк + один `join` | 9.3 / 9.4 / 10.4 мс   |

**Что сделать:** одна рекурсия, `push` в общий `string[]`, `Buffer.from(parts.join(''))`
в конце. Заодно: `zipSetText` передаёт `Buffer` с `{ binary: false }` — привести к явному
виду и покрыть тестом на не-ASCII содержимое.

**Риск:** низкий. **Выигрыш:** ~×2.7 на сериализации. **Оценка:** ~0.5 дня.

### 4.3. Мелочи из того же ряда

- `commands/parse.ts:isBuiltIn` прогоняет 14 регулярных выражений на каждую команду
  без префикса — достаточно взять первое слово и проверить по `Set`.
- `reportUtils.ts:getNextSibling` делает `siblings.indexOf(node)` — линейный поиск на
  каждый шаг вбок; на абзаце с сотнями `w:r` это квадратично. Замерить до правки.

## 5. Этап 2 — реестр команд вместо `switch`

**Проблема.** Знание об одной команде размазано по шести местам:

- `Command` (enum в `types.ts`);
- `BUILT_IN_COMMANDS` + `builtInRegexes`/`isBuiltIn` (`commands/parse.ts`);
- `EXPRESSION_COMMANDS` — где подставляются алиасы операторов, дублирует знание из `switch`;
- `CommandPrefix` и цепочка `if/else` в `getCommand`;
- `switch` в `commands/execute.ts:processCmd`;
- `if (isLoopExploring(ctx)) return;` — повторён 5 раз внутри этого `switch`.

Добавление команды требует правки всех шести.

**Что взять у docxtemplater.** `module-wrapper.js`: модуль объявляет набор хуков, ядро
(`render.js`, `parser.js`) перебирает модули и не знает ни про циклы, ни про raw-xml.
`matchers()` объявляет префиксы данными вместо `if (cmd[0] === '@')`.

**Что сделать.** `commands/registry.ts`:

```ts
type CommandSpec = {
  /** Подставлять ли алиасы операторов в тело команды. */
  isExpression: boolean;
  /** Пропускать ли команду на разведочном проходе цикла. */
  skipWhileExploring: boolean;
  run: (args: CommandArgs) => Promise<string | void>;
};

const COMMANDS: Record<Command, CommandSpec> = { … };
```

`processCmd` становится поиском по таблице с общим `try/catch` и общей проверкой
`skipWhileExploring`; `EXPRESSION_COMMANDS` и список built-in выводятся из реестра;
префиксы `*`/`=`/`!` — таблица вместо `if/else`.

**Проверка:** тест «каждый член `Command` присутствует в реестре» (перебор
`Object.values(Command)`) — новую команду нельзя забыть подключить.

**Риск:** низкий. **Оценка:** ~1–1.5 дня.

## 6. Этап 3 — декларативные правила структуры OOXML

**Проблема.** Правила «что docx считает валидным» зашиты в поток управления `walk.ts`:
вставка `w:p` в опустевший `w:tc` живёт прямо посреди `moveOutputUp`; четыре разных
правила удаления (разведочный проход, абзац с `w:drawing`, строка-обёртка вложенной
таблицы, ячейка многоячеечной конструкции) — в одной функции `dropDeadOutputNode`;
три почти одинаковых блока `if (ctx.pendingXNode && tag === …)` для IMAGE/LINK/HTML.

**Что взять у docxtemplater.** `file-type-config.js` описывает это данными
(`tagShouldContain`, `expandTags`), починка применяется одним проходом в
`join-uncorrupt.js`, а не по ходу рендера.

**Что сделать.** `src/docx/structure.ts` с таблицами: `TAG_SHOULD_CONTAIN` (какой тег
какого ребёнка обязан иметь и чем добирается), `PENDING_SLOTS` (куда подставляется
готовый узел IMAGE/LINK/HTML), `DROP_RULES` (именованные предикаты удаления).
`walk.ts` перебирает таблицы вместо ветвлений.

**Плюс:** правила становятся юнит-тестируемыми отдельно от обхода — сейчас непокрытые
ветви сосредоточены именно здесь (`execute.ts` 90.79% ветвей, `walk.ts` 95.29%).

**Риск:** средний — самая тонкая часть движка. Гейт: золотой корпус этапа 0 без диффа.
**Оценка:** ~1 день.

## 7. Этап 4 — ошибки с адресом и стабильными кодами

**Проблема.** При `failFast: false` бросается массив ошибок, в котором не указано,
**в какой части документа** каждая возникла: отчёт рендерит `document.xml`,
`header1.xml`, `footer1.xml`, и всё сливается в один список. Позиции в шаблоне тоже нет.
Для сценария из README («пользователи делают шаблоны интерактивно») это ровно та
информация, которой не хватает.

**Что взять у docxtemplater.** Каждая ошибка несёт
`properties: { id, explanation, offset, xtag, file, context }`; `file` проставляется
централизованно (`xml-templater.js:errorChecker`); мультиошибка агрегируется в
`properties.errors` (`throwMultiError`); `id` — машиночитаемый код, чтобы не парсить текст.

**Что сделать:** общий предок `TemplateError` с `properties { id, part?, command?, explanation? }`;
стабильные `id` для всех классов; проставление `part` в одном месте `main.ts` перед броском.
Имена классов, тексты сообщений, поле `command` и формат броска массивом — без изменений
(это поведенческий контракт, §2). Добавление свойств поведение не меняет.

**Риск:** низкий. **Оценка:** ~0.5–1 день.

## 8. Этап 5 — разделить состояние: `Context` на части

Раньше это откладывалось до мажора, потому что `Context` протекал в публичный `.d.ts`.
Теперь — в плане.

**Проблема.** `Context` — 27 полей, смешивающих четыре разные вещи:

| что                           | поля                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| состояние обхода              | `level`, `fJump`, `buffers`, `cell`, `pIfCheckMap`, `trIfCheckMap`                                                                                       |
| состояние сбора команды       | `fCmd`, `cmd`, `fSeekQuery`, `query`                                                                                                                     |
| скоуп данных                  | `vars`, `loops`, `shorthands`, `jsSandbox`                                                                                                               |
| ресурсы фич (IMAGE/LINK/HTML) | `images`, `links`, `htmls`, `pendingImageNode`, `pendingLinkNode`, `pendingHtmlNode`, `imageAndShapeIdIncrement`, `linkId`, `htmlId`, `textRunPropsNode` |

Десять полей из двадцати семи принадлежат трём командам, но объявлены в типе ядра, и
`walk.ts` читает их напрямую. Ровно то, что docxtemplater держит внутри модулей.

**Что сделать:**

- `WalkState`, `Scope`, `Resources` как отдельные объекты; `Context` — их композиция
  (`ctx.walk`, `ctx.scope`, `ctx.resources`) либо явная передача аргументами;
- `Resources` получает собственный интерфейс (`addImage`, `addLink`, `addHtml`,
  `takePending(tag)`), которым пользуются `commands/media.ts` и `walk.ts` — счётчики
  `linkId`/`htmlId`/`imageAndShapeIdIncrement` перестают быть общим достоянием;
- заодно уходит венгерская нотация, унаследованная от апстрима (`fCmd`, `fJump`,
  `fSeekQuery`, `gCntIf`, `gCntEndIf`) — имена вроде `isCollectingCommand`,
  `jumpRequested`, `openIfCount`;
- `runJs` получает суженный контекст (см. оговорку в §2) — решение фиксируется в changeset.

**Риск:** низкий по поведению (чистое перекладывание), заметный по объёму диффа.
Делать **после** этапа 3, иначе два больших диффа наложатся на один и тот же `walk.ts`.
**Оценка:** ~1–1.5 дня.

## 9. Этап 6 — компиляция шаблона отдельно от рендера

Главное, что есть у docxtemplater и чего нет здесь. С поведенческим контрактом это
стало выполнимо: `createReport` снаружи не меняется вообще.

**Проблема.** Сейчас один проход делает пять дел сразу: обходит дерево, собирает
команды, интерпретирует управляющие конструкции прыжками назад, строит выходное дерево
и копит ресурсы. Отсюда самые дорогие по сложности места движка:

- **разведочный проход** (`EXPLORATION_PASS`): каждая конструкция `FOR`/`IF` обходится
  минимум дважды — сначала «вхолостую», чтобы понять, пуст ли цикл и какая ветка `IF`
  выбрана;
- **прыжки назад** (`fJump`, `refNodeLevel`, `deltaJump`, подъём выходного курсора
  на `deltaJump` уровней) — арифметика уровней, которую нельзя проверить локально;
- **удаление уже выпущенных узлов** (`dropDeadOutputNode`): узел эмитится, потом
  вынимается из выхода, но остаётся связан с родителем, чтобы обход мог через него подняться;
- **`pIfCheckMap`/`trIfCheckMap`**: два `IF` в одном абзаце дерутся за один узел при
  прыжке и зацикливают обход — лечится рантайм-стражем вместо структурной проверки;
- **мутация входного дерева**: `execute.ts` пишет `node._ifName` в узлы шаблона, поэтому
  распарсенный шаблон нельзя переиспользовать, а `Node` несёт поле состояния рендера;
- **`listCommands` притворяется рендером**: гоняет полноценный `walkTemplate` с подставным
  `CommandProcessor`, который лезет в приватное состояние (`ctx.cmd = ''`, `ctx.shorthands`);
  `extractQuery` — третий обход с флагом `fSeekQuery` в горячем пути `processText`.

**Что взять у docxtemplater.** `compile()` строит `postparsed` — структуру шаблона;
`render(data)` её потребляет; `getTags()`/`InspectModule` читают ту же структуру.
Ошибки структуры (незакрытый цикл, `ELSE` вне `IF`) находятся до обращения к данным.
Итерация цикла — рекурсивный рендер поддерева, а не прыжок курсора.

**Что сделать (фазами, каждая проходит золотой корпус):**

1. **Фаза A — `compile`.** Один проход по дереву строит `TemplateProgram`: список
   команд с их узлами и, для `FOR`/`IF`, границы тела и ветвей. Пока ничего не
   рендерит. На нём сразу строятся `listCommands` и `extractQuery` — три обхода
   становятся одним, `fSeekQuery` уходит из `processText`, подставной `CommandProcessor`
   исчезает. `_ifName` переезжает в структуру, входное дерево перестаёт мутироваться.
2. **Фаза B — структурные проверки на компиляции.** Незакрытый `FOR`, лишний `END-IF`,
   `ELSE` вне `IF`, два `IF` в одном абзаце — проверяются по структуре. Тексты и классы
   ошибок сохраняются дословно (контракт), но `pIfCheckMap`/`trIfCheckMap` и
   `collectUnterminatedConstructErrors` уходят.
3. **Фаза C — рендер по структуре.** Рекурсивная генерация выхода: тело цикла
   рендерится N раз, ветка `IF` — та, что выбрана. Уходят `EXPLORATION_PASS`, `fJump`,
   `deltaJump`, `dropDeadOutputNode` (пустой абзац/строку/ячейку видно **до** эмиссии).
   Побочный выигрыш к этапу 1: каждая конструкция перестаёт обходиться дважды.

**Честно о риске.** Это единственный этап, который может не сойтись. Текущее поведение
в углах (какой именно абзац исчезает, когда удаляется ячейка, как ведёт себя
`FOR` внутри `IF` внутри строки таблицы) — во многом эмерджентное следствие порядка
операций в обходе. Воспроизвести его точно более чистой моделью — работа, объём которой
честно оценивается только после фазы A. Поэтому:

- фазы A и B полезны сами по себе и не ломают модель выполнения — их можно взять
  и остановиться;
- фаза C начинается только если золотой корпус этапа 0 покрывает все фикстуры,
  и откатывается целиком, если корпус не сходится.

**Оценка:** фаза A ~1.5 дня, фаза B ~1 день, фаза C ~3–5 дней. **Риск:** A/B низкий,
C высокий.

## 10. Этап 7 — валидация опций (требует решения о релизе)

`options.ts:resolveOptions` молча проглатывает ошибки вызывающего:

```ts
errorHandler: typeof options.errorHandler === 'function' ? options.errorHandler : null,
```

Передали не-функцию — обработчик просто не работает, без единого слова. Неизвестные
ключи (опечатка `procesLineBreaks`) игнорируются. `template` не проверяется вовсе —
неверный тип всплывает невнятной ошибкой JSZip.

**Что взять у docxtemplater.** `minizod.js` — 200 строк собственной мини-схемы (чтобы
не тащить зависимость) + `.strict()`: опечатка в опции падает сразу и понятно.

**Решение за мейнтейнером** — это единственный пункт плана, меняющий поведение:

- **строго**: бросать на неверный тип и на неизвестный ключ. Ловит реальные баги, но
  код, который сегодня «работает» с мусорной опцией, начнёт падать → **minor** с явным
  упоминанием;
- **мягко**: бросать только на фатальном (`template` неверного типа), остальное в
  `logger.debug`. Полностью совместимо.

Рекомендация: строго — для типов существующих опций, мягко — для неизвестных ключей
(их и так ловит TypeScript, а в JS-проектах строгость чаще мешает).

**Оценка:** ~0.5 дня.

## 12. Порядок и суммарная оценка

```
Этап 0  Страховка: золотой корпус, listCommands-снапшоты, bench      1.0 дн   риск —
Этап 1  Перф: контекст песочницы, buildXml                           1.0 дн   риск средний/низкий
Этап 2  Реестр команд                                                1.5 дн   риск низкий
Этап 3  Декларативные правила структуры OOXML                        1.0 дн   риск средний
Этап 4  Ошибки с адресом и стабильными кодами                        1.0 дн   риск низкий
Этап 5  Разделение Context; переименования                           1.5 дн   риск низкий
Этап 6  Компиляция отдельно от рендера   A 1.5 + B 1.0 + C 3–5 дн     5.5–7.5  риск A/B низкий, C высокий
Этап 7  Валидация опций                                              0.5 дн   риск: решение о релизе
                                                                     ────────
                                                          без фазы C  ~8.5 дн
                                                          с фазой C   ~12–14 дн
```

Порядок неслучаен: этап 1 даёт самый заметный выигрыш и не трогает модель выполнения;
2 и 3 разгружают `execute.ts` и `walk.ts` **до** того, как за них возьмётся этап 6;
5 идёт после 3, чтобы два крупных диффа не наложились на один файл; 6 — последним,
когда всё вокруг уже упрощено, а страховка обкатана на пяти предыдущих этапах.

**Точка выхода.** После этапа 5 кодовая база уже забирает почти всё ценное из
docxtemplater: развязку команд, декларативные правила, адресуемые ошибки, разделённое
состояние — при этом ни одна правка не меняет модель выполнения. Этап 6 — отдельное
решение, которое стоит принимать по результатам фазы A, а не заранее.

**Критерий приёмки каждого этапа:**

1. `npm run verify` зелёный;
2. золотой корпус этапа 0 — без диффа (единственное исключение: этап 4, где меняются
   только добавленные поля ошибок);
3. `npm run bench` не хуже предыдущего замера;
4. changeset: `patch` для 0–3, 5, 6; `minor` для 4 (новые поля) и 7 (если строгий вариант).
